**Quality gate** — погоджена умова, яка блокує прийняття. Markdown-правило
скеровує агента; автоматичне блокування потрібно налаштувати в runner/CI.
Посилання на тест або `[x]` у tasks не доводить, що тест виконувався.

Приклади простежуваності:

- [FR-EXPORT-01](requirements.md#реєстр-для-поточного-зрізу): E2/U1/U2 → tasks
  2.1, 2.2, 3.2, 3.3 → точні usage IDs у файлі та відповідність поточним filters.
- [BC-PRIVACY-01](requirements.md#реєстр-для-поточного-зрізу): E8–E10 → tasks
  2.1, 3.2, 3.3, 3.4 → default prompts=[], точні opt-in IDs, контрольована мутація.
- [NFR-ACCESS-01](requirements.md#реєстр-для-поточного-зрізу): U3 → tasks
  2.2, 3.3, 4.2 → labels, клавіатура, фокус, viewport 375 px. Markup test B
  не замінює browser interaction після wiring.
- [BC-COMPAT-01](requirements.md#реєстр-для-поточного-зрізу): E1/E3/E4/E11 → tasks
  2.1, 3.2, 4.2 → старий default all, strict request validation та opt-in round trip.

## Propose → apply → archive і виявлений борг

Під час **propose** узгодьте позитивні, негативні й граничні сценарії та
додайте перевірки до задач. Під час **apply** реалізуйте їх разом із кодом,
запустіть погоджені команди й запишіть результати. Перед **archive** перевірте
інтегровану ревізію, findings і докази; у workshop потрібен людський review.

Локальна [схема OpenSpec 1.13.0](https://github.com/Fission-AI/OpenSpec/blob/v1.13.0/schemas/spec-driven/schema.yaml)
вимагає способу перевірки в кожній задачі. **Apply не гарантує автоматичного
запуску всього test suite.** `openspec validate` перевіряє артефакти OpenSpec,
а [archive CLI](https://github.com/Fission-AI/OpenSpec/blob/v1.13.0/src/core/archive.ts)
не є тестуванням продукту. Правило «архів лише після доказів» походить також
із нашого AGENTS.md; його не замінює успішне переміщення зміни в archive.

| Коли виявлено прогалину | Що робимо |
| --- | --- |
| Apply виконано, зміна відкрита; бракує перевірки її поведінки | Доповнюємо поточні tasks і тести. Уточнюємо specs, лише якщо треба змінити вимогу. Не відкладаємо необхідний доказ під назвою «борг». |
| Потрібна поведінка поза погодженим scope | Спочатку погоджуємо scope й пов'язані артефакти; worker не розширює задачу сам. |
| Зміна вже archived | Створюємо нову пов'язану зміну на виправлення або покращення тестів. Історію попереднього рішення зберігаємо. |

Для суто тестової зміни без нової поведінки OpenSpec 1.13.0 підтримує
`skip_specs: true` у `.openspec.yaml`. Не вигадуйте продуктову вимогу лише
заради формату. Це не спосіб прибрати потрібні сценарії з поточної feature.

На інтегрованому стані після targeted unit/API checks запускайте окремо:

```text
npm run check
npm run build
npm run test:e2e
```

Build перед browser suite обов'язковий: поточний Playwright config піднімає
production server на 3100 з тимчасовою SQLite-базою. Після виправлень повторіть
affected checks і required gates. Read-only checker читає код та докази;
orchestrator додає і запускає тести. Порядок і ownership — у [prompts](prompts.md).

## Playwright: перевіряємо результат користувача

Слабкий приклад залежить від CSS, вгадує час і не перевіряє експорт:

```ts
const button = page.locator(".btn");
await button.click();
await page.waitForTimeout(2000);
expect(await button.isVisible()).toBe(true);
```

Нижче **схематичне тіло майбутнього тесту**, а не готовий файл чи виконаний
прогін. Передумови: ізольований synthetic fixture U1/U2/U3 з
[прикладу E8 у context packet](context-packet.md); лише U1
має model=unknown-lab; у базі також є prompts PA/PB/PC. Тест сам готує стан,
відкриває export controls та встановлює **лише model=unknown-lab**. Є `page`,
`testInfo`, імпорти `expect`, `readFile` з `node:fs/promises` і `BundleSchema`
з `src/lib/schema.ts`. ID-очікування виведені вручну зі fixture.

```ts
await page.getByRole("radio", {
  name: "Current filters", exact: true,
}).check();
await expect(page.getByLabel("Include prompts in export", {
  exact: true,
})).not.toBeChecked();

const pending = page.waitForEvent("download");
await page.getByRole("button", {
  name: "Download JSON", exact: true,
}).click();
const output = testInfo.outputPath("export.json");
await (await pending).saveAs(output);
const bundle = BundleSchema.parse(
  JSON.parse(await readFile(output, "utf8")),
);
expect(bundle.usage.map(row => row.id).sort()).toEqual(["U1"]);
expect(bundle.prompts).toEqual([]);
expect(bundle.machines.map(row => row.id).sort()).toEqual(["A"]);
```

Це доказ конкретного зрізу [FR-EXPORT-01/02 і BC-PRIVACY-01](requirements.md#реєстр-для-поточного-зрізу),
не всього export contract. Окремо перевірте all за замовчуванням, opt-in,
порожній результат, invalid request та помилку download/retry. Для
[NFR-INTEGRITY-01](requirements.md#реєстр-для-поточного-зрізу) потрібні також
точні token counts, незмінність входу й repeated import.

Role/label locators і `await expect(locator)` допомагають дочекатися UI-стану;
звичайний `expect` підходить уже прочитаному JSON. Очікування download
реєструється **до** click; `saveAs` чекає завершення завантаження. Контролюйте
дані й зовнішні залежності: окремий browser context не ізолює спільну БД.
Джерела: [Playwright best practices](https://playwright.dev/docs/best-practices),
[downloads](https://playwright.dev/docs/downloads),
[застереження щодо hard waits](https://playwright.dev/docs/api/class-page#page-wait-for-timeout).

## Візуальна якість: чому зелений тест пропустив зміщені іконки

Окремий приклад із `08-visual-quality`: користувач помітив, що символи
провайдерів у Overview розташовані нижче центра квадратів. Це не реалізація
`06-scoped-export` і не зміна обсягу головної вправи дня04.

Попередні перевірки підтверджували поведінку й відсутність горизонтального
overflow. Скріншоти справді переглядали, але без достатнього огляду дрібних
елементів. На зменшеному знімку такий дефект легко пропустити; попередній
огляд його не виявив. Висновок
«visual review виконано» був надто широким щодо фактично перевірених деталей.

У коді символ був текстовим Unicode-знаком. Контейнер мав 28×28px, а успадкована
висота рядка при 22px шрифті становила 33px. CSS центрував рядок тексту, а не
видимі штрихи символу. Навіть `line-height:1` не гарантує однакового вигляду
на всіх системних шрифтах. Збалансована SVG-геометрія прибирає цю залежність.

| Рівень перевірки | Конкретне питання | Доказ і межа |
| --- | --- | --- |
| Функціональний | Чи показано правильного провайдера й дані? | Assertions тексту/даних; не доводять візуальний баланс. |
| Геометричний | Чи збігається центр видимого рисунка з центром його місця? | Порівняння фактичних bounds у браузері, допуск 1 CSS px для цього компонента. Сам SVG viewport може бути центрований, а path усередині — ні. |
| Візуальний | Чи виглядає рисунок збалансованим, чи немає обрізання/нерівного відступу? | Огляд сторінки в контексті та компонентних crops у масштабі 1:1; геометрія не замінює зорове сприйняття. |
| Regression | Чи змінився схвалений вигляд? | Screenshot diff після незалежного схвалення baseline; помилковий baseline лише закріплює дефект. |

**Візуальний quality gate перед «готово»:**

1. Orchestrator формулює видимий результат, стани й viewport. Наприклад:
   обидва знаки центровані, не обрізані, однакові в model rows і badges.
2. Maker перевіряє реалізацію в браузері. Для зміненого спільного компонента
   переглядає також його типових споживачів, а не лише щойно змінений екран.
3. Checker окремо оглядає повний контекст і crops в реальному розмірі:
   вирівнювання, відступи, текст, іконки, контраст, overflow, focus і помилки.
   Завдання «знайди конкретні візуальні дефекти» має власний результат,
   незалежний від звіту «тести зелені».
4. Для цього дефекту browser check порівнює bounds намальованої SVG-групи,
   перетворені в координати екрана, із центром контейнера. Контрольоване
   зміщення рисунка на 4px має провалити той самий assertion; відновлення — пройти.
   Це перевірка чутливості до зміщення, не доказ усієї візуальної якості.
5. У журналі записують viewport, перевірені стани/компоненти, файли зображень,
   висновки checker, виправлення й неперевірений обсяг. Фактичні результати
   прикладу 08 зберігаються в [build log](../build-log.md), не в порожньому шаблоні.

Постійне правило вже має місце в `AGENTS.md`; для Claude Code той самий
контракт потрібно передати через інструкції, які цей інструмент справді читає.
Markdown задає процедуру. Автоматичне блокування дає виконуваний browser test;
людський/агентний візуальний огляд усе одно має бути реально виконаний.

## Готовий skill: процедура, спостереження й oracle

Для вправи рекомендуємо
[web-design-reviewer із github/awesome-copilot](https://github.com/github/awesome-copilot/blob/main/skills/web-design-reviewer/SKILL.md).
Це готова процедура огляду layout, responsive states, доступності й візуальної
узгодженості; вона передбачає браузерні знімки та повторну перевірку виправлень.
**Саме встановлення не є перевіркою продукту й не гарантує pixel-perfect.**

| Частина | Її робота в нашому процесі |
| --- | --- |
| Skill — процедура | Підказує, на що дивитися та як оформити findings. Не надає доступ до браузера автоматично. |
| Browser tool — спостереження | Відкриває справжній UI, перемикає стани, дає screenshots і DOM. Сам знімок не означає, що його оглянули. |
| Oracle — підстава прийняття | Погоджений видимий критерій, reference або незалежно виведене expected. Визначає, яка різниця є дефектом. |
| Checker — окрема відповідальність | Зіставляє спостереження з oracle, називає конкретні невідповідності й межі огляду. |

За бажанням ведучий або учасник **до заняття** переглядає поточний `SKILL.md`
та встановлює лише цей skill у вибраний coding agent:

```text
npx skills add github/awesome-copilot --skill web-design-reviewer
```

Команда додає інструкції, а не налаштовує браузерний доступ. Перевірте, що ваш
агент завантажив skill і справді вміє відкривати сторінку та бачити зображення.
У звіті вкажіть джерело й revision skill. У цьому уроку встановлення не
виконане автоматично; якщо skill недоступний, той самий review contract є в
[prompt 5a](prompts.md#5a-visual-checker--окремий-доказ-для-ui).

Оригінальний skill включає виправлення коду. У нашому DAG **visual checker
працює без source edits**: знаходить дефект, maker виправляє, checker повторно
оглядає. Браузерні дії й створення proof artifacts дозволені окремо. Це
узгоджена роль уроку, а не твердження, що сам skill завжди read-only.

### Design critique, fidelity і regression — різні питання

| Вид оцінки | Питання | Потрібна основа |
| --- | --- | --- |
| Design critique | Чи зрозуміло й зручно користувачу? | Задача користувача, правила доступності, інформаційна ієрархія. |
| Reference fidelity | Наскільки реалізація відповідає погодженому зразку? | Доступний reference того самого стану, дозволені відхилення. |
| Visual regression | Чи змінився раніше схвалений вигляд? | Перевірений baseline та повторюване середовище. |

Для clone спочатку зафіксуйте reference, assets і шрифти, viewport, device
pixel ratio (кількість фізичних пікселів на CSS-піксель), масштаб браузера,
тему, дані, час, scroll і UI-стан. Порівнюйте однакові умови; лише width
недостатньо. Screenshot diff показує різницю пікселів, overlay накладає два
зображення для пошуку зміщення. Відмінність ще треба пояснити: це може бути
дефект або різниця рендерингу.

[Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)
дає `toHaveScreenshot()` для повторного порівняння. Новий baseline спершу
оглядають; автоматичне оновлення expected до поточного дефектного UI приховає
проблему. Допуски та маски динамічних областей погоджують заздалегідь, не
послаблюють після failing test. Критичну перевірювану ділянку не маскують.

Token Atlas поки не має доступного погодженого Claude Design reference.
Тому тут робимо critique, геометричні перевірки й огляд регресій; **фідельність
до недоступного дизайну не заявляємо**. Встановлення skills, clone чужого
сайту й новий screenshot-baseline suite не є частиною `06-scoped-export`.

### Читабельний екран може містити незрозумілі дані

Навчальний приклад із синтетичними labels: у кожному рядку сесії стоять
`CodexLabUser` та обрізаний UUID. Навіть якщо текст вирівняний і contrast
достатній, користувач не розуміє, чим сесії відрізняються. UUID — технічний
ідентифікатор; його можна лишити в деталях, але не вважати поясненням роботи.
Обговоріть, які безпечні метадані допоможуть вибору: дата, проєкт, тривалість,
провайдер. Не вигадуйте session title і не показуйте приватний prompt без
погодженого контракту.

Напис `Codex` у довільній назві користувача чи машини не доводить провайдера
сесії. `Claude Code` у badge може бути правильним або ні — screenshot цього
не встановлює. Перевіряємо походження: source adapter → normalized provider →
stored record → UI. У synthetic fixture задайте label із назвою іншого
провайдера та перевірте, що label не перевизначає provenance. **Не лікуйте
неоднозначність перейменуванням провайдера за підрядком.**

Це окремий case study інформаційної якості. Він не додає нові requirements до
scoped export і не заявляє, що виправлення runtime уже завершене. Завдання
checker — розділити доведений UX-дефект, гіпотезу про дані й потрібний доказ.

## Метрики допомагають, але не визначають якість самі

| Сигнал | Що він не доводить |
| --- | --- |
| Statement/branch coverage — виконаний код | Чи assertion розрізняє правильний і неправильний результат; чи реалізована пропущена вимога. |
| Mutation score — виявлені мутації у визначеному наборі | Відсутність усіх дефектів; результат залежить від mutators, scope, exclusions і знаменника. |
| Архітектурні тести — виконання заданих правил залежностей | Правила, яких немає в тестах, або придатність продукту для користувача. |

Фіксуйте baseline разом із revision, командами, налаштуваннями та складом коду
і тестів. Пороги й baseline змінюйте через review. Не дозволяйте агенту
автоматично «покращувати якість на +5%», послаблювати gate чи вилучати складні
випадки заради числа. Розрізняйте відсотки й відсоткові пункти; універсального
порога для кожного проєкту немає. У цьому lab coverage/mutation runner не
оголошені встановленими й жодної нової метрики не виміряно.

Задача **3.4** має окремий доказ: на collision fixture з **лише model-фільтром**
opt-in дає [U1]/[PA]/[A]. Той самий тест проходить → matcher тимчасово змінено
на sessionId-only → assertion падає через зайві prompts → повний tuple
відновлено → тест проходить. Fixture й expected не змінюються. Syntax/import
failure не зараховується. Це чутливість до одного дефекту, не загальний доказ
якості; еквівалентні мутації потребують окремого аналізу.

U1/U2/U3 доступний maker і **не є held-out**. Для 3.4 checker додатково
готує окремий collision dataset і expected, які не розкриває maker до join.
Orchestrator повторює негативний контроль на ньому та записує обидва набори.
Незалежне авторство, прихованість кейсу та здатність тесту виявити баг — три
різні властивості; fresh chat сам по собі не забезпечує всі три.
Джерела: [ISTQB CTFL §4.3](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf),
[Stryker metrics](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/),
[equivalent mutants](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/).

## Окремий приклад: acceptance для AI-workflow

**Це не функція Token Atlas.** Уявімо агента, який готує чернетку відповіді
підтримки. Текст може різнитися; приймаємо поведінку за критеріями.

Сценарій: **Given** у дозволених джерелах немає потрібного факту; **When** агент
отримує запит; **Then** він позначає нестачу даних і ескалює питання визначеній
людині, не вигадує відповідь і сам не надсилає повідомлення.

Eval-протокол до запуску фіксує:

- версію synthetic cases, входи, дозволені джерела, потрібні факти та expected escalation;
- фактичний model ID, параметри, prompt, tools і середовище;
- число кейсів **N** та повторів кожного **R**; обидва значення потрібно погодити
  й записати, а не добирати після результату;
- rubric: підтверджені факти, відповідність запиту, правильне рішення про
  ескалацію; критерії pass/fail і поріг прийняття;
- tool traces, рішення про ескалацію, кінцевий стан, результати всіх N×R спроб
  та причини провалів. Частота успіху = успішні спроби / усі спроби.

LLM-grader застосовує rubric, а його оцінки звіряють із людськими прикладами.
Не вибирайте лише найкращу відповідь і не припускайте статистичної незалежності
повторів. Успіх на наборі має межі: нові випадки можуть поводитися інакше.
Це запропонований протокол без виміряних результатів чи універсального порога.
Метод: [Anthropic — evals для агентів](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

Окремо діють **детерміновані межі**, які quality score не може компенсувати:

| Власник | Відповідальність у навчальному прикладі |
| --- | --- |
| Product owner разом із QA | Business scope, consent, acceptance/rubric: дозволено читати погоджені джерела й готувати draft; надсилання потребує рішення людини. |
| Tech / security owner | Дозволені tools, schema аргументів, авторизація та runtime restrictions; adapter відхиляє send без дозволу. |
| Orchestrator | Stop за відсутності даних, конфлікту правил чи вичерпання бюджету; передає конкретне питання й докази, не розширює права сам. |
| Призначена людина | Вирішує ескальовану неоднозначність і погоджує конкретну дію через визначену процедуру. |

Hard check: неавторизований send відхилено **і** повідомлення не потрапило у
вихідну чергу. Перевіряємо побічний ефект, а не лише слова агента. Заборона в
prompt сама не забезпечує цей контроль; критичні ліміти реалізує runtime.
Розподіл ролей — приклад угоди команди, не універсальний стандарт посад.
