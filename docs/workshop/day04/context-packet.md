# День 04: пакет контексту для worker

**Пакет контексту** — коротке доручення з потрібними джерелами, погодженими
вимогами, станом коду й критеріями прийняття. Передаємо його до запуску worker.
Історія чату може допомогти скласти пакет, але сама не визначає контракт.

Це шаблон і навчальний приклад для [уроку](guide.md). Приклад описує майбутню
роботу над `06-scoped-export`; він не підтверджує реалізацію чи запуск тестів.
Повні [prompts ролей](prompts.md) доповнюють пакет.
Стабільні IDs та їхні межі визначає [реєстр вимог](requirements.md).

## Review перед dispatch

Розділіть зміст обговорення за статусом. Для кожного пункту додайте джерело
та версію або дату. Приватні повідомлення й персональні дані в пакет не копіюйте.

| Статус | Що означає | Що потрібно перед використанням |
| ------ | ---------- | ------------------------------- |
| Факт | Перевірене твердження про наявний стан | Посилання на код, документ або результат перевірки |
| Рішення | Погоджений вибір щодо бажаної поведінки | Власник рішення та запис погодження |
| Припущення | Твердження, яке ще не перевірили | Спосіб перевірки й наслідок помилки |
| Відкрите питання | Відсутня відповідь, потрібна для роботи | Хто відповідає та які задачі залежать від відповіді |

Звірте нотатки з поточним репозиторієм. Різниця між старою та запланованою
поведінкою може бути метою зміни. Суперечність між вимогою, DTO і фікстурою
потребує рішення до залежного кроку. Worker повертає джерела, конкретну
суперечність і пропозицію orchestrator. Самостійно змінювати вимоги або
очікуваний результат тесту для усунення суперечності не можна.

## Який контекст додавати

- **Сталі правила репозиторію:** стек, межі даних, команди перевірки.
- **Scoped rules:** правила певної області, наприклад browser-тестів.
- **Специфікація зміни:** поведінка, сценарії та межі саме цієї функції.
- **Task brief:** конкретна роль, файли, вхідні дані, ліміти та форма повернення.
- **Evidence:** фактичні результати для checker, прийняття та handoff.

Наявність файла не доводить, що його вміст потрапив до контексту. Механізм
пошуку scoped rules залежить від harness і робочої теки. Явно перелічіть
потрібні файли в дорученні або додайте їх через доступний механізм контексту.
До редагування перевірте робочу теку, ревізію, читання потрібних джерел і
відсутність невирішених суперечностей. Текстове правило не створює sandbox.

## Шаблон для повторного використання

```text

Статус контексту:

- Припущення + перевірка:
- Відкрите питання + власник/залежність:

Вимога → сценарій → незалежне очікування → потрібний доказ:
Точний interface:
Дозволені файли для запису:
Спільні inputs лише для читання та їхній власник:
Поза обсягом:
```

Для недоступних метрик запишіть `unavailable`, не `0`.

## Приклад: Worker A, selector Token Atlas

Ціль: реалізувати чисту функцію вибору export bundle та її unit-тести.
Значення позначені нижче; перед dispatch треба вписати фактичні runtime-поля
та завершити review.

**Стан і джерела:**

- Початковий продукт: tag `workshop-day04-start`; фактичний commit запишіть
  через `git rev-parse workshop-day04-start`. Цей стан передує новому контракту.
- Спільна база worker: **`<SHA погодженого контракту — заповнити>`**.
  Orchestrator спочатку створює й комітить DTO, синтетичні fixtures та DAG.
  Обидва workers мають читати ці передумови з одного commit.
- Робоча тека, режим, фактична модель і dirty state: **заповнити перед стартом**.
- Прочитати [правила репозиторію](../../../AGENTS.md),
  [proposal](../../../openspec/changes/06-scoped-export/proposal.md),
  [design](../../../openspec/changes/06-scoped-export/design.md),
  [team-exchange spec](../../../openspec/changes/06-scoped-export/specs/team-exchange/spec.md)
  та `src/lib/schema.ts`. Після checkpoint також прочитати
  `src/lib/export-contract.ts` і `src/lib/export-fixtures.ts`.

**Вимоги та очікуваний доказ:**

| ID вимоги уроку | Джерело поведінки | Сценарій та доказ для A |
| --------------- | ---------------- | ---------------------- |
| [`FR-EXPORT-01`](requirements.md#реєстр-для-поточного-зрізу) | [Explicit export scope](../../../openspec/changes/06-scoped-export/specs/team-exchange/spec.md#requirement-explicit-export-scope) | E2/E7: точні IDs перетину фільтрів, включні UTC-межі, unknown model і значення порожніх filters |
| [`BC-PRIVACY-01`](requirements.md#реєстр-для-поточного-зрізу) | [Explicit prompt export](../../../openspec/changes/06-scoped-export/specs/team-exchange/spec.md#requirement-explicit-prompt-export) та [PRD, P8](../../PRD.md#mvp-requirements) | E8/E9/E10: повний session tuple, власна дата prompt, відсутність тексту без opt-in |
| [`TC-STACK-01`](requirements.md#реєстр-для-поточного-зрізу) | [Architecture: Runtime](../../architecture.md#runtime) і [правила репозиторію](../../../AGENTS.md) | Наявний Node 24/npm/TypeScript strict; review diff і unit run для A, check/build для інтегрованої ревізії |

ID посилається на вимогу, але не замінює її повного тексту. Докази записуємо
в [evidence-template](evidence-template.md#перевірки) з командою, станом коду й
фактичним результатом. [Task 2.1](../../../openspec/changes/06-scoped-export/tasks.md)
визначає доручення A. API validation, browser flow та фінальні гейти належать
інтегрованій перевірці orchestrator.
Порожній bundle, незмінність input, server boundary та сумісність `all`
також мають IDs у реєстрі: `FR-EXPORT-02`, `NFR-INTEGRITY-01`,
`TC-SERVER-01`, `BC-COMPAT-01`. Три рядки вище показують основний ланцюжок,
а не скасовують решту вимог selector.

**Статус контексту для review:**

| Статус | Пункт |
| ------ | ----- |
| Факт про джерело | У Context поточного design початковий export описано як весь source. Перед роботою звірити цей опис із кодом на зазначеному baseline. |
| Рішення до підтвердження review | `all` зберігає поточну поведінку; `filtered` застосовує погоджені правила вибору usage, prompts і machines. Власник прийняття вимог — людина. |
| Припущення / передумова для перевірки | DTO й fixtures мають бути доступні на SHA контракту. Перевірити їхні exports та відповідність spec; за розбіжності dispatch зупиняється. |
| Відкрите до старту | Фактичний SHA контракту, cwd/режим, модель і підтвердження review. Orchestrator заповнює ці поля. |

**Interface та межі:**

```ts
selectExportBundle(bundle: Bundle, selection: ScopeSelection,
  includePrompts = false): Bundle
```

- Запис лише в `src/lib/export-scope.ts` і `src/lib/export-scope.test.ts`.
- DTO й fixture imports дозволені лише як читання. Власник
  `src/lib/export-contract.ts` і `src/lib/export-fixtures.ts` — orchestrator.
- Функція не мутує input, зберігає IDs, token buckets та `exportedAt`.
  Не читає SQL, filesystem, network, pricing або глобальний state.
- `all` зберігає usage/machines і включає prompts лише за явним opt-in,
  включно з prompt-only sessions. У `filtered` залишаються лише machines,
  на які посилаються обрані usage/prompts. Unknown models не відкидаються.
- Worker не змінює API, UI, shared fixtures, DTO, package/lock/config,
  OpenSpec/tasks або докази інших ролей. Значення `source` і runtime validation
  обробляє orchestrator на межі API, не selector.

**Один конкретний acceptance scenario: E8.** Усі записи синтетичні й мають
однакову допустиму UTC-дату. Machines A/B мають однакову мітку member.
`U1/U2/U3` у цій таблиці — IDs записів usage; це не номери UI-сценаріїв
`U1/U2/U3` з dashboard spec.

| Usage ID | Machine | Provider | Session | Model | Human prompt |
| -------- | ------- | -------- | ------- | ----- | ------------ |
| U1 | A | codex | shared | unknown-lab | PA |
| U2 | B | codex | shared | other | PB |
| U3 | A | claude-code | shared | other | PC |

За `scope=filtered`, `includePrompts=true` і **лише** `model=unknown-lab`
очікування: usage `[U1]`, prompts `[PA]`, machines `[A]`. Provider/member/date
фільтри тут порожні, щоб не приховати помилку ключа. За `includePrompts=false`
на тих самих даних очікуємо порожні prompts. Ці expected IDs виведені вручну
зі spec, не обчислені функцією, яку тестуємо.

Це один сценарій, не повне покриття. A також перевіряє перетин фільтрів,
UTC-межі, empty result, immutability та `all` compatibility. Після створення
тесту виконує:

```text
npm test -- src/lib/export-scope.test.ts
```

Повернення містить команду, exit code й actual output. Import/syntax failure
не зараховується як поведінковий red. Для незалежного негативного контролю
orchestrator пізніше виконує task 3.4 на інтегрованому коді: слабкий ключ
`sessionId` має дати red, відновлений composite key — green. Заздалегідь
позначати цей контроль виконаним не можна.

**Ліміт і рішення:** 12 хвилин — навчальний timebox, а не гарантія примусової
зупинки інструмента. Без нових залежностей і рекурсивного делегування. На
межі часу або за потреби змінити DTO/shared file worker повертає partial
state. Orchestrator координує зміну інтерфейсу та нову спільну базу, а людина
погоджує зміну продуктового scope або privacy-вимоги. Невизначене рішення
не перетворюється на дозвіл через очікування.

## Короткий handoff після ліміту

```text
Status: partial / blocked
Мета, requirement IDs:
Base SHA / HEAD / cwd / режим / dirty files:
Завершено з доказом: [сценарій → команда → actual result]
Не перевірено або не завершено:
Остання команда й помилка:
Наступна одна дія та її перевірка:
Потрібне рішення, власник:
Не змінювати: DTO, fixtures та файли інших ролей.
```

Orchestrator перевіряє, що попередній worker більше не пише файли, перш ніж
передати їх іншому. Наступний виконавець читає контракт і diff, звіряє стан
дерева та продовжує незавершену роботу. Наявність handoff не закриває task і
не підміняє фінальну перевірку.
