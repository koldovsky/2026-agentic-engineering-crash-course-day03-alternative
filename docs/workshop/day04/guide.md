# День 04 — від вимог до оркестрації та доказів

**17.09.2026 · 150 хв · Codex · продовження Token Atlas дня 03.**

Центральне питання: як передати одну зміну кільком виконавцям і довести, що
після інтеграції працює саме погоджена поведінка? Спочатку класифікуємо вимоги
і обираємо вертикальний зріз, потім учасники будують DAG, задають
контракти workers, відділяють maker від checker і приймають результат за доказами.

**Статус матеріалу:** сценарій заняття і підготовлена OpenSpec-зміна. Реалізація
`06-scoped-export`, її тести, виміряна тривалість і day04 checkpoints ще не
підтверджені. Команди нижче — інструкції до майбутнього прогону, а не його запис.
Матеріали й підготовлена зміна входять у публічний стартовий тег
`workshop-day04-start`. [Browser handout](https://koldovsky.github.io/2026-agentic-engineering-crash-course/day04-lab.html)
і [source-bundle ZIP](https://koldovsky.github.io/2026-agentic-engineering-crash-course/day04-materials.zip)
доступні окремо для читання та перенесення навчальних матеріалів.

## Звідки продовжуємо

Використовуємо [Token Atlas day03-alternative](https://github.com/koldovsky/2026-agentic-engineering-crash-course-day03-alternative),
стан `workshop-day04-start`, який продовжує day03 checkpoint `workshop-05-dashboard`.
У ньому вже є Claude/Codex ingest, SQLite, ціни,

писати парсер або pricing для демонстрації паралелізму не потрібно.

Нова потреба: **експортувати вибраний зріз usage**, зберігши нинішній повний експорт
за замовчуванням і явну згоду на включення prompts. Це одна OpenSpec-зміна
`06-scoped-export`, всередині якої є дві незалежні роботи після фіксації контракту.
Номер `05-reference-design` лишається зарезервованим за недоступним дизайн-референсом.
Цей урок його не закриває і не заявляє відповідності дизайну.

Послідовність курсу:

| День | Що переносимо в сьогоднішню роботу                                        |
| ---- | ------------------------------------------------------------------------- |
| 01   | Як помітимо помилку? Як відкотимо? Який незалежний доказ переконає?       |
| 02   | Мінімальний контекст для ролі, короткий звіт, передача стану файлом       |
| 03   | Намір → сценарії до коду → перевірки → архів лише завершеної зміни        |
| 04   | DAG, orchestrator-worker, вибір моделі, вартість workers, maker ≠ checker |

Вісь дня — **Orchestration**. Два workers не отримують права самі розширювати
обсяг, міняти контракт, публікувати результат або закривати роботу один одного.
Circuit breaker, unattended loop і фабрика проєктів залишаються темою дня 05.

## Що учасник має розуміти до демонстрації

Після теоретичного блоку учасник може:

- класифікувати FR/NFR/TC/BC, відрізнити capability slice від задачі worker
  та простежити вимогу до сценарію й доказу;
- перетворити чат на погоджений context packet і пояснити, де живуть сталі
  правила, критерії конкретної зміни та результати;
- оцінити якість тесту за oracle, ізоляцією та перевіреною поведінкою, назвати
  межі coverage і вимоги до оцінювання недетермінованої AI-функції;

- відрізнити модель, агента, роль і workflow, пояснити різницю між оркестрацією
  та автономністю;
- прочитати DAG, назвати передумови вузла, знайти незалежні задачі й пояснити,
  чого чекає join;
- скласти контракт worker та обґрунтувати, чому selector і controlled UI можна
  реалізувати окремо;
- відрізнити ізоляцію контексту, робочих файлів і дозволів, назвати точний стан
  коду, якого стосується перевірка;
- сформулювати інваріант, отримати незалежне очікування та побудувати
  контрприклад, який здатен спростувати «готово»;
- окремо оцінити elapsed time і повну вартість роботи, обрати модель під задачу
  та визначити умову зупинки.

Перевірка розуміння: дайте учаснику нову малу зміну й попросіть пояснити поділ,
залежності та спосіб прийняття результату без назв конкретних інструментів.
Token Atlas далі показує застосування цих понять на одному продукті.

## Теоретичний маршрут: як читати схеми

### 05–20: намір, вимоги й один вертикальний зріз

Capability slicing починається з корисного результату для користувача.
S1 «експортувати вибраний зріз» проходить через UI, API, selector і файл.
Worker A та B — задачі всередині S1, кожна окремо не завершує capability.
FR задають поведінку, NFR — якість, TC — технічні межі, BC — продуктові
правила. Ця класифікація не визначає порядок запуску; залежності задає DAG.

Пройдіть [реєстр і матрицю вимог](requirements.md): FR-EXPORT-01 → S1 → E2/U1
→ tasks 2.1/2.2/3.2/3.3 → точні IDs у завантаженому JSON. Чинні P/E/U IDs
збережено. Таблиця не заміняє доказ: поки прогону немає, статус planned.

### 20–42: агенти, координація та залежності

Модель генерує відповіді. Агент використовує модель разом із контекстом,
інструментами та циклом отримання зворотного зв'язку. Роль задає відповідальність
у конкретній роботі: orchestrator координує, worker виконує обмежене завдання,
checker шукає порушення погодженої поведінки. Назва ролі не визначає модель чи
дозволи автоматично.

Оркестрація відповідає на питання «хто виконує яку роботу, у якому порядку й
як передає результат». Автономність описує, які рішення агент може приймати
без людини. Кілька workers можуть мати дуже вузькі повноваження, а один агент
може вести довгий автономний цикл. У
[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
Anthropic розрізняє заздалегідь визначені workflows і системи, де модель
динамічно обирає подальші дії. Це корисна архітектурна відмінність, а не
універсальна шкала якості.

[DAG за визначенням NIST](https://xlinux.nist.gov/dads/HTML/directAcycGraph.html)
є орієнтованим графом без циклів. У нашій схемі вузол позначає роботу з
результатом, стрілка — залежність від цього результату. Вузол готовий до
запуску, коли отримав усі потрібні передумови. Agent-role і task-node не
тотожні: orchestrator виконує кілька різних вузлів.

Спочатку намалюйте послідовність «контракт, selector, UI, інтеграція». Потім
покажіть, що selector та UI після фіксації interface не потребують результатів
одне одного. Їх можна запустити через fan-out. Join чекає на обидва прийнятні
результати. Стан `blocked` чи `partial` потребує рішення координатора.
Саме повідомлення `done` ще не є доказом завершення.

Критичний шлях — найдовший за тривалістю ланцюг залежних робіт. Він пояснює,
чому додатковий worker не прискорить послідовну передумову. Повторне виправлення
після checker розглядаємо як нову спробу з новою ревізією. DAG однієї спроби
не слід плутати з усім циклом доопрацювань або графом Git-комітів.

### 42–52: контракт та межі роботи

Контракт поєднує вхід, результат, поведінку, помилки й критерії прийняття.
DTO описує лише форму даних, які частини системи передають одна одній.
Type-only DTO не перевірить JSON під час виконання: цю межу перевіряє API schema.
Фіксація контракту до dispatch дозволяє незалежним workers однаково розуміти
`scope="all"` і `scope="filtered"`.

Pure selector залежить від явних аргументів, не читає SQLite чи файли й не
змінює вхідний bundle. Його можна перевірити малими фікстурами. Controlled UI
отримує поточне значення через `value` і повідомляє про зміну через `onChange`.
Parent володіє цим станом і запитом на експорт. Так поділ A/B випливає з
архітектури, а не просто з бажання використати двох агентів.

Окремий context відділяє історію розмови. Worktree відділяє checkout файлів.
Sandbox визначає дозволені операції. Правило ownership у prompt саме по собі
не створює sandbox. Git може злити різні файли без конфлікту, хоча UI й API
виявляться несумісними. Тому file isolation не скасовує спільного контракту
та інтеграційної перевірки.

### 52–60: перетворення чату на контекст

Чат — джерело для уточнення, а не автоматично погоджена специфікація.
Відділіть факти, прийняті рішення, припущення та відкриті питання; звірте
з repo revision і джерелами. Суперечність повертається власнику рішення.
Після review збережіть сталі правила в інструкціях, поведінку — у specs,
а worker передайте мінімальний потрібний packet із посиланнями й межами.
Шаблон і приклад: [context-packet.md](context-packet.md).

### 60–67: routing, час і вартість

Routing призначає модель або виконавця під конкретну роботу. У прикладі
важливі складність контракту, ризик помилки й доступна перевірка. Результат
порівнюємо після однакових сценаріїв прийняття, включно з доопрацюваннями.

Latency, або elapsed time, — час від старту до отримання прийнятого результату.
Повна вартість включає orchestrator, workers, checker і повторні спроби.
Для двох незалежних workers ідеалізований час паралельної частини становить
`max(T_A, T_B)`, а не суму їхніх тривалостей. До нього додаються підготовка,
інтеграція, перевірка та фактичні затримки. Це модель без конкуренції за
ресурси, не обіцянка прискорення.

Числа в навчальних розрахунках часу й вартості є **умовними прикладами**, якщо
біля них немає посилання на виміряний прогін. Вони не задають ціну моделі,
ліміт підписки чи результат Token Atlas. Timebox у prompt є домовленістю;
примусова зупинка потребує окремого механізму виконання.

### 67–85: звідки береться очікуваний результат

Інваріант описує властивість, яка має виконуватися для всіх допустимих входів
у заданій області. Наприклад, без `includePrompts=true` експорт не містить
prompts за жодного scope. Oracle — незалежна основа для визначення правильного
результату. У малій фікстурі це очікувані IDs, виведені зі сценарію вручну.
Обчислення expected через selector, який тестуємо, повторить його помилку.

Контрприклад є конкретним входом, на якому поведінка порушує вимогу.
Негативний контроль перевіряє саму здатність тесту помітити порушення:
тимчасово послаблюємо session key й очікуємо падіння того самого assertion.
Після відновлення ключа повторюємо перевірку. Падіння через import error
не доводить, що privacy-сценарій працює.

Окремий checker отримує сценарії й код, формує findings та спосіб відтворення.
У базовому lab він не змінює source files, а запропоновані перевірки запускає
orchestrator. Окремий контекст послаблює вплив пояснень maker, але не гарантує
відсутності спільної помилки у вимогах. Результат приймаємо за відтворюваними
доказами й людським review. Unit перевіряє selector, API — межу запиту,
browser — поведінку користувача та фактичний download. Зелені перевірки
окремих workers не замінюють перевірку інтегрованого стану.

Правила якості тестів і критерії feature — різні рівні. Тести плануємо в
propose, реалізуємо й запускаємо під час apply, докази перевіряємо до archive.
Apply не є автоматичним запуском suite; validate не перевіряє поведінку продукту.
Після archive нову роботу ведемо як пов'язану зміну, зберігаючи історію.

Розберіть слабкий і сильний Playwright-приклади: стабільний locator, очікування
події до click, ізольований state і точні assertions у завантаженому JSON.
Coverage показує виконані ділянки, не силу перевірки. Для AI-поведінки поза
Token Atlas потрібні versioned cases, rubric, повтори, конфігурація та tool
trace; permission checks окремо доводять жорсткі межі. Повні відповіді:
[quality.md](quality.md).

Окремо розберіть готовий `web-design-reviewer`: skill задає процедуру,
browser tools дають спостереження, oracle задає критерій правильності.
Установлення skill саме не забезпечує ні браузерного доступу, ні якості.
Інструкції та optional install — у [quality](quality.md#готовий-skill-процедура-спостереження-й-oracle).
Вправа з review: незалежний checker оглядає loaded UI при desktop/375px,
page context і crops 1:1; builder виправляє findings, checker перевіряє знову.
Порівняйте вирівнювання видимого рисунка і зрозумілість labels: обидва
впливають на якість, але потребують різних доказів. Ім'я з `Codex` не є
доказом provider — перевіряємо provenance, не підрядок.

Для pixel-perfect потрібен доступний погоджений reference та однакові
viewport/state/fonts/rendering environment. Approved baseline — оглянутий
еталон для регресій; screenshot поточного UI не стає ним автоматично.
Ці case studies не розширюють `06-scoped-export` і не означають завершених fixes.

## Терміни поруч із прикладом

| Термін                     | Як читати в цьому уроці                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Capability / vertical slice | Здатність продукту дати результат / малий завершений шлях через потрібні шари |
| FR / NFR / TC / BC | Поведінка / якість / технічні межі / бізнесові та UX-правила |
| Context packet | Перевірений набір джерел, рішень, критеріїв і меж для однієї ролі |
| Visual-review skill / browser tool | Інструкція огляду / інструмент, який дає доступ до rendered UI та зображень |
| Reference fidelity / visual regression | Відповідність погодженому зразку / зміна раніше схваленого вигляду |
| Baseline / screenshot diff | Схвалений еталон / видима різниця між знімками, яка потребує пояснення |
| Eval / rubric / trial | Оцінювання на кейсах / правила оцінки / одна спроба |
| Tool trace | Журнал викликів інструментів, аргументів, результатів і рішень |
| Decomposition              | Поділ зміни на роботи з явними входами, результатами й залежностями                                        |
| Bounded assignment         | Завдання з обмеженим обсягом, власними файлами, перевіркою та умовою зупинки                               |
| Fan-out / join             | Запуск незалежних робіт / очікування й поєднання потрібних результатів; join не є назвою Git-команди       |
| DTO                        | Data Transfer Object: погоджена форма даних між частинами системи, тут scope і filters                     |
| Pure function              | Функція без зовнішніх побічних ефектів, результат якої залежить від явних входів                           |
| Controlled UI              | Компонент, для якого parent задає значення, а callback повідомляє про намір його змінити                   |
| Wiring                     | З'єднання готових частин: schema, route, parent state і controls                                           |
| Revision / SHA / HEAD      | Стан коду / ідентифікатор commit / Git-посилання на поточний commit; незакомічений diff обліковуємо окремо |
| Worktree / sandbox         | Окрема робоча тека Git / межа дозволів виконання; одне не забезпечує інше                                  |
| Fixture                    | Невеликий підготовлений набір вхідних даних; у цьому уроці лише синтетичний                                |
| Invariant / oracle         | Властивість, яку треба зберегти / незалежна основа для визначення правильного результату                   |
| Counterexample / assertion | Вхід, який спростовує твердження про правильність / перевірювана умова в тесті                             |
| Held-out check             | Випадок, прихований від maker до незалежної перевірки; оприлюднений приклад ним не є                                   |
| Gate                       | Перевірка, результат якої дозволяє або зупиняє перехід до наступного етапу                                 |
| Latency / cost             | Час до результату / повні витрати на всі залучені виклики й повторні спроби                                |
| Handoff                    | Коротка передача фактичного стану, доказів, незавершеної роботи й наступної дії                            |

Вправа для самоперевірки перед командами: позначте на DAG спільний контракт,
fan-out, join і фінальний gate. Назвіть один інваріант експорту й очікувані
IDs фікстури без запуску selector. Поясніть, які саме дані й дозволи потрібні
кожній ролі. Далі наведено операційні кроки того самого прикладу.

## Контракт вправи: що саме будуємо

Джерело поведінки — сценарії й `design.md` у зміні `06-scoped-export`.
Guide пояснює їх, але не замінює. Перед workers перевірте узгодженість.

| Межа                  | Погоджена поведінка                                                                                |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| Запит                 | `{ source, includePrompts, scope, filters }`; нинішні клієнти без нових полів працюють             |
| Defaults              | `source="local"`, `includePrompts=false`, `scope="all"`; відсутні filters означають порожній набір |
| `all`                 | Усі usage вибраного source; за явного `includePrompts=true` — усі його prompts, як раніше          |
| `filtered`            | AND-фільтрація usage за provider, member, exact model, from, to                                    |
| Дати                  | Валідні `YYYY-MM-DD`, включні UTC-дні; `from > to` — помилка, навіть для `all`                     |
| Зайві поля            | `q`, `page` і невідомі вкладені ключі не входять у контракт; API відхиляє їх                       |
| Filters при `all`     | Валідні filters дозволені, але не обмежують результат; невірні значення відхиляються               |
| Невідомі моделі       | Usage зберігається; відсутність ціни не є причиною його відкинути                                  |
| Prompts у `filtered`  | Лише за явною згодою, з власними provider/member/date, і лише з ключем сесії вибраного usage       |
| Ключ сесії            | Трійка `(machineId, provider, sessionId)`, не один `sessionId`                                     |
| Machines у `filtered` | Лише machines, на які посилаються залишені usage/prompts                                           |
| Порожній зріз         | Валідний version-1 bundle з порожніми масивами                                                     |

Prompt не має поля model. Тому model визначає **сесії вибраного usage**, а не
«модель, що написала prompt». Навіть без model-фільтра filtered prompts повинні
належати вибраному usage. Prompt-only сесії залишаються доступними в `all`, але
не проходять через `filtered`. Пошук `q` і номер сторінки prompt view не звужують
експорт. UI показує саме це; не називайте результат «поточною сторінкою».

Type-only DTO orchestrator створює в `src/lib/export-contract.ts` до розгалуження:
`ExportScope`, `ExportFilters`, `ScopeSelection`. Разом із DTO orchestrator
готує deterministic synthetic fixtures у `src/lib/export-fixtures.ts` і DAG,
перевіряє та комітить їх як спільну передумову. Fixture-файл належить orchestrator.
Після review фіксуємо:

```text
selectExportBundle(bundle, selection, includePrompts = false): Bundle

ExportScopeFields props:
  value: ExportScope
  onChange: (scope: ExportScope) => void
  filters: ExportFilters
  disabled?: boolean
```

`ExportScopeFields` показує radio «All data» / «Current filters» (`all` / `filtered`), видимий read-only summary
фільтрів і «All usage matches», коли filters порожні. Parent тримає state,
передає актуальні dashboard filters, fetch і privacy-checkbox. UI worker не
імпортує SQLite, server queries чи runtime pricing у client code.

## DAG, ownership і join

```text
Human review → Orchestrator: freeze scenarios + DTO + fixtures + DAG + base revision
                              ├→ A: pure selector + unit tests ─┐
                              └→ B: scope fields + markup tests┤
                                                               ↓ JOIN
                 Orchestrator: API validation + route + parent wiring
                                                               ↓
                 Independent checker: scenarios + findings
                                                               ↓
                 Orchestrator: held-out tests + integrated gates
                                                               ↓
                 Human verdict → archive only after verification
```

Checker може спроєктувати свої тести раніше, читаючи сценарії без maker-висновків.
Фінальний review і приймальні перевірки мають стосуватися **інтегрованої** ревізії.

| Роль         | Дозволені записи                                                                                                          | Результат передачі                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Orchestrator | DTO, synthetic fixtures, DAG, `transfer.ts`, export route, parent controls/wiring, інтеграційні тести, OpenSpec, evidence | Зафіксований контракт, integrated revision, гейти             |
| Worker A     | `src/lib/export-scope.ts`, `src/lib/export-scope.test.ts`                                                                 | Selector, сценарії, фактичні unit results                     |
| Worker B     | `src/components/export-scope-fields.tsx`, `src/components/export-scope-fields.test.ts`                                    | Controlled UI, ізольовані markup assertions, фактичні results |
| Checker      | Жодних source edits; читає специфікацію, diff, тести                                                                      | Файл/рядок, порушений сценарій, спосіб відтворення            |

Worker B використовує `.test.ts`, а не `.test.tsx`: наявний Vitest працює в Node
і знаходить `.test.ts`. Для focused markup assertions достатньо `createElement`
та `renderToStaticMarkup`; browser interactions перевіряємо після інтеграції.

Workers не змінюють `tasks.md`, lockfile, shared DTO, `transfer-controls.tsx` чи
файли іншого worker. Coordinator один оновлює галочки після доказів. Зміна
контракту означає зупинку обох workers, оновлення design і нову спільну базу.

**False parallelism:** «A робить API, B робить UI», але обидва одночасно змінюють
DTO й `transfer-controls.tsx`. Навіть clean merge може з'єднати різні значення
`scope`. Нехай аудиторія виправить цей DAG до запуску: спершу спільний контракт,
потім незалежні файли, далі один інтегратор. За потреби покажіть конфлікт на
одноразовому текстовому файлі у disposable clone; не подавайте постановку як
виявлений дефект продукту.

## Subagent і worktree — різні види ізоляції

Окремий контекст subagent не гарантує окрему робочу теку. У shared workspace
правки workers одразу видимі іншим. Перевірте фактичний режим вашого Codex;
не вважайте spawn автоматичним `git worktree`.

Основний варіант уроку: native subagents із непересічним ownership. Coordinator
планує інтеграційні тести, поки workers працюють; не запускає паралельні коміти
чи build в одній теці. Якщо автоматичні subagents недоступні, два термінали в
окремих worktrees дають явну файлову ізоляцію. Це два скоординовані запуски, а не
доказ того, що конкретний клієнт підтримує native orchestration.

Після review orchestrator створює DTO, `src/lib/export-fixtures.ts` і DAG, перевіряє їх
та комітить разом з OpenSpec-артефактами. Перевірте clean tracked state і
наявність цих файлів у prerequisite commit: baseline tag їх ще не містить.
Лише після цього обидва worktrees стартують від однієї ревізії:

```text
git status --short
git rev-parse HEAD
git worktree add -b codex/day04-selector ../token-atlas-worker-a HEAD
git worktree add -b codex/day04-fields ../token-atlas-worker-b HEAD
git worktree list
```

В окремому терміналі кожного worker: `cd ../token-atlas-worker-a` або
`cd ../token-atlas-worker-b`, далі `npm ci`, `codex` і відповідний prompt.
Кожен worktree має власні залежності; не копіюйте `.env`, локальну БД чи logs.
Workers звітують про commit SHA і перевірки. Після перевірки file ownership
coordinator інтегрує їх по одному:

```text
git diff --stat HEAD...codex/day04-selector
git diff --stat HEAD...codex/day04-fields
git merge --no-ff codex/day04-selector
git merge --no-ff codex/day04-fields
```

Ці merge-команди застосовні тільки до worktree-варіанта з комітами. У shared
workspace немає worker-гілок для merge: coordinator перевіряє єдиний diff і
робить узгоджений коміт. Не видаляйте робочі теки, доки є невраховані зміни.

Серійний fallback: той самий контракт → A → B → інтеграція → checker → гейти.
Межі ролей і незалежність checker залишаються. Перекриття задач у часі (concurrency) підтверджують
реальні часові інтервали. Користь такої схеми потребує вимірювання; кількість вікон її не доводить.

## Перевірка, що може спростувати «готово»

До коду checker складає окремі синтетичні приклади: однаковий `sessionId` на
двох machines; той самий id у різних providers; prompt поза датою при usage
всередині дати; невідома model; порожній зріз; відсутність нових полів запиту.
Для collision-сценарію фільтр **лише `model=unknown-lab`**: цю модель має usage
однієї сесії, а інші machines/providers мають такий самий `sessionId` з іншою
моделлю. Provider/member/date-фільтри тут порожні, щоб вони не приховали
помилкове зіставлення лише за `sessionId`.
Очікувані IDs обчислюємо вручну. Не використовуйте selector, щоб створити
очікуваний результат його ж тесту.

Обов'язковий негативний контроль для задачі 3.4 — три usage records на однакову
дату, machines A і B з одним member Ada:

| Usage ID | Machine | Provider    | Session | Model       | Prompt тієї ж сесії |
| -------- | ------- | ----------- | ------- | ----------- | ------------------- |
| U1       | A       | codex       | shared  | unknown-lab | PA                  |
| U2       | B       | codex       | shared  | other       | PB                  |
| U3       | A       | claude-code | shared  | other       | PC                  |

При `scope=filtered`, `includePrompts=true` і **лише** `model=unknown-lab`
очікуємо usage IDs `[U1]`, prompt IDs `[PA]`, machine IDs `[A]`. Інших фільтрів
немає. У контрольованій локальній мутації тимчасово замініть composite session
key на один `sessionId`: exact-set assertion мусить впасти через зайві prompts.
Відновіть правильний ключ і повторіть той самий тест до green. Не залишайте
мутацію в фінальному diff. Запишіть обидва actual results у
[evidence-template.md](evidence-template.md) і build log; без спостереженого
red → restore → green задача 3.4 лишається незавершеною. Тут описано майбутню
перевірку, а не заявлено, що її вже виконано.

Показаний U1/U2/U3 — спільний навчальний приклад; worker його вже знає.
Він доводить чутливість до дефекту, але **не є held-out**. Для вимоги задачі
3.4 checker також готує окремий collision-випадок з іншим набором synthetic
записів і незалежним expected set. До завершення worker-коду дані й expected
залишаються тільки у checker/orchestrator. На інтеграції запускаємо той самий
негативний контроль і на цьому наборі; зберігаємо обидві перевірки в evidence.
Після розкриття набір стає regression test, а не новим прихованим тестом.

Checker віддає сценарії й findings без правок. Orchestrator додає held-out
API/browser тести і перевіряє їх на інтегрованому коді. Fresh context зменшує
успадкування maker-припущень; інша модель може дати ще один погляд, але не є
гарантією незалежності або правильності.

| Доказ               | Що саме перевірити                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| Негативний контроль | Тест нового filtered behavior падає на baseline через потрібну поведінку, а не через syntax/import error |
| Unit                | Вибрані IDs, UTC межі, composite session key, prompt exclusion, unknown model                            |
| API                 | Defaults, strict validation, `all` compatibility, порожній valid bundle, privacy                         |
| Browser             | Реальний вибір scope, актуальні filters, default opt-out, downloaded JSON, keyboard labels               |
| Integrated gates    | Точна перевірена ревізія; lint/types/tests/specs, production build, acceptance                           |

У фінальній інтегрованій теці:

```text
git rev-parse HEAD
git status --short
npm run openspec -- validate 06-scoped-export --strict --no-interactive
npm test -- src/lib/export-scope.test.ts
npm test -- src/components/export-scope-fields.test.ts
npm run check
npm run build
npm run test:e2e
```

Якщо тести нового сценарію ще не створені, існуючий зелений suite його не
підтверджує. Вкажіть це в evidence. `npm run check` містить lint, typecheck,
Vitest і strict OpenSpec validation; browser acceptance — окрема команда.
Власна зелена перевірка worker не підміняє інтегрований build.

Будь-яка правка після checker-review змінює об'єкт перевірки: заново перевірте
зачеплені сценарії й фінальні гейти. Прозове «PASS» checker не перекриває
червоні асерти. Після реального проходження завершіть tasks і викличте
`$openspec-archive-change 06-scoped-export`; потім `npm run spec:validate`.

## Бюджет, ліміти й передача роботи

До dispatch заповніть таблицю. Значення встановлює ведучий під доступний план;
порожня клітинка не означає нуль або безліміт. Інструмент може не показувати
worker-specific tokens: тоді запис `unavailable`, не оцінка зі стелі.

| Роль         | Модель / effort     | Хвилин максимум | Output budget | План $ API-equivalent | Факт / джерело |
| ------------ | ------------------- | --------------- | ------------- | --------------------- | -------------- |
| Orchestrator | заповнити до старту | —               | —             | —                     | not run        |
| A            | заповнити до старту | —               | —             | —                     | not run        |
| B            | заповнити до старту | —               | —             | —                     | not run        |
| Checker      | заповнити до старту | —               | —             | —                     | not run        |

Model routing пояснюємо вимогами: інтеграція/privacy потребують уважного міркування;
вузький UI-контракт може підійти швидшій доступній моделі. Якщо клієнт не дає
модель на роль, залиште успадковану й запишіть факт. Не обіцяйте конкретний
прапорець або hard token cap без перевірки у встановленій версії.

Рахуйте також coordinator, checker, повторні спроби й очікування. API-equivalent
USD — оцінка за відомими цінами, не рахунок підписки. Невідома ціна — `unpriced`.
Один parallel-run без порівнянного serial-run не доводить прискорення чи економію.
Не читайте особисті agent logs для навчальної таблиці: беріть показані клієнтом
метрики або спеціально підготовлені синтетичні дані з відповідною позначкою.

Stop conditions: спільний файл поза ownership; невизначений контракт; повторна
невдала спроба без нової гіпотези; вичерпаний час/ліміт. Worker повертає стан,
diff/commit, останню команду й помилку, зроблене/не зроблене, наступний крок.
При rate limit не запускаємо нову копію того самого запиту безконтрольно:
зберігаємо handoff, продовжуємо іншу незалежну роботу або serial fallback.

команди, exit codes, число тестів, висновки checker й обмеження. Не замінюйте
історичні результати дня 03 новими числами.

| Сценарій               | Команда / артефакт         | Ревізія | Результат | Рішення |
| ---------------------- | -------------------------- | ------- | --------- | ------- |
| Filtered usage         | заповнити після прогону    | —       | not run   | pending |
| Prompt consent + scope | заповнити після прогону    | —       | not run   | pending |
| `all` compatibility    | заповнити після прогону    | —       | not run   | pending |
| Independent checker    | файл звіту / повідомлення  | —       | not run   | pending |
| Production + browser   | команди й фактичний output | —       | not run   | pending |

Домашнє завдання і критерії здачі — у [homework.md](homework.md).
Робочі prompts — у [prompts.md](prompts.md).
